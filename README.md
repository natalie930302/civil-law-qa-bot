# LangChain_Linebot — 公務人員法規問答系統

用 LangChain 框架整合 LINE Bot 的法規問答系統,讓使用者透過 LINE 對話查詢公務人員相關法規,並附上法規來源摘錄。

## 運作流程

1. 透過 LINE Bot 接收使用者問題
2. 用 LangChain 在向量資料庫(`chroma_db_langchain`)中檢索相關法規內容
3. 透過 OpenAI GPT 產生法規說明回答
4. 自動附上法規來源摘錄回傳給使用者

## 檔案說明

- `setup_database.py` — 讀取 `datasets/` 底下的法規文件,建立 Chroma 向量資料庫(需先執行)
- `app_langchain.py` — 主程式,處理 LINE Webhook、LangChain 檢索與 GPT 回答生成
- `chroma_db_langchain/` — 向量資料庫檔案

## 技術棧

Python + LangChain + Chroma(向量資料庫)+ OpenAI GPT + LINE Messaging API

## 環境設定

複製 `.env.example` 為 `.env`,並填入以下金鑰:

```

```


## 檢索品質評估(2026/09 新增)

原本的系統只做到「能回答」,沒有量化過檢索品質。這輪補上人工標註的評估集,量測 RAG 系統最關鍵的一環:「檢索有沒有真的撈到對的法條」。

- `src/parse_laws.py`:把 `datasets/` 裡的 4 部法規 PDF 切成逐條 JSON(`eval/articles_clean.json`,139條乾淨資料)
- `eval/eval_questions.json`:24 題手動撰寫、人工核對過 `gold_id` 的真實問題,涵蓋全部 4 部法規,跟訓練/建庫語料完全不重疊(避免資料洩漏)
- `src/eval_retrieval.py`:評估 baseline embedding(`paraphrase-multilingual-MiniLM-L12-v2`)vs. TSDAE 領域微調後的 embedding

### 結果

| 方法 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| **Baseline(未微調)** | **0.458** | **0.625** | **0.667** | **0.555** |
| TSDAE 領域微調後 | 0.167 | 0.250 | 0.250 | 0.218 |

### 重要發現:TSDAE 微調反而讓檢索變差,不是變好

這是繼 `food-violation-severity-model` 的 BERT 負向結果後,第二個誠實記錄的「直覺上應該更好、但實際更差」案例。TSDAE 是無監督領域微調法,理論上只用 139 條法規條文語料訓練,不需要人工標註問答配對,應該能讓 embedding 更貼近法規領域的語言風格。但實際結果全面下滑(MRR 0.555 → 0.218)。

推測原因:
- **語料量太小**:139 條條文對一個要重新調整整個 embedding 空間的模型來說遠遠不夠,3 epoch、54 個訓練 step 就讓模型偏離了原本通用語義空間的品質(`train_loss` 收斂在 10.6,明顯沒有學到穩定的重建能力)
- **TSDAE 的訓練目標(去噪重建句子)跟下游任務(語義檢索排序)不一致**,語料量不足時,這種目標不一致比訓練帶來的領域適應效果影響更大,等於是用一個訓練不充分的重建任務把原本檢索能力很好的通用多語embedding「洗壞」了
- 呼應 `food-violation-severity-model` 得到的同一個原則:**模型複雜度/訓練策略要跟資料量匹配**,資料量不夠時貿然微調反而有害,不是保底也能持平

## 用 LoRA 驗證「災難性遺忘」假設(2026/09 新增)

上面的負向結果,理論上符合機器學習裡的 **Catastrophic Forgetting(災難性遺忘)**:全參數微調在只有139條語料的小資料集上,訓練目標(去噪重建)跟下游任務(語義檢索)不一致,足以蓋掉/破壞原本在大規模語料上學到的通用多語語義空間。這不只是憑直覺推測,而是可以直接驗證的假設——如果原因真的是「全參數微調動到了太多不該動的權重」,那麼凍結大部分原始權重、只微調一小部分參數(LoRA / PEFT,近年參數效率微調的主流做法,原因正是為了避免這個問題),應該就能大幅緩解。

`src/eval_retrieval_lora.py` 用同樣的139條語料、同樣的TSDAE去噪重建訓練目標,但只在 attention 的 query/value 插入低秩 adapter,凍結 99.87% 的原始參數(可訓練參數 147,456 / 117,801,216)。

### 結果:LoRA 幾乎完整保留了原本的檢索能力

| 方法 | Recall@1 | Recall@3 | Recall@5 | MRR | 可訓練參數比例 |
|---|---|---|---|---|---|
| **Baseline(未微調)** | 0.458 | 0.625 | 0.667 | 0.555 | — |
| **LoRA 微調後** | **0.458** | **0.625** | 0.625 | **0.544** | 0.13% |
| 全參數微調 | 0.167 | 0.250 | 0.250 | 0.218 | 100% |

LoRA 版本的 MRR(0.544)幾乎跟 baseline(0.555)打平,Recall@1/3 完全相同,只有 Recall@5 略降一點點——跟全參數微調的全面崩盤(MRR掉到0.218)是天壤之別。**這個對照直接驗證了「小資料下全參數微調的問題出在動到了太多權重」這個假設**:同一份139條語料、同一個訓練目標,只是把可訓練參數從100%降到0.13%,檢索品質的破壞幾乎完全消失。

### 一個意外插曲:LoRA 不是自動免疫,超參數沒調好一樣會壞

第一次嘗試時,依照「LoRA通常可以用比全參數微調更高的學習率」這個常見經驗法則,把學習率設成 3e-4(比全參數微調的 3e-5 高10倍),結果**比全參數微調還要更差**——檢索完全失效(MRR=0.024),而且是一種不同的失效模式:不是遺忘,而是**表徵坍縮(representation collapse)**,任兩篇完全不同法規條文算出來的embedding,cosine相似度高達0.9996,等於模型不管輸入什麼都輸出幾乎一樣的向量。這是靠診斷embedding本身(檢查是否NaN、算相似度)才抓到的,不是單純看最終分數判斷。把學習率調回跟全參數微調一致的 3e-5 之後,才得到上面那組乾淨的正向結果。

這個插曲本身也是一個值得記錄的發現:**「LoRA 對超參數不敏感/更穩健」不是可以無腦套用的通則**,在極小資料集(139筆)的無監督重建任務上,學習率選擇仍然是決定成敗的關鍵變因,LoRA 降低的是「訓練動到的權重量」,不是「訓練不穩定的風險」。

## 資料量門檻的另一半驗證:單純擴大語料量,全參數微調還是會崩壞(2026/09 新增)

LoRA 驗證的是「凍結大部分權重」這個緩解手段。還有一個沒回答的問題:如果不用 LoRA,單純把語料量做大,全參數微調是否就不再崩壞?合併 23 個相關公務人員法規類別(來源:Hugging Face `lianghsun/tw-law`,官方同步自法務部全國法規資料庫)後,語料從139條擴大到**872條(6.3倍)**,確保原本24題評估集的 gold_id 全數保留在擴充後的語料庫裡,用完全相同的超參數(3 epoch、batch_size=8、lr=3e-5)重跑一次全參數 TSDAE 微調。

### 結果:資料量放大 6.3 倍,不但沒有變好,反而更差

| 方法 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| Baseline(872條語料,未微調) | 0.500 | 0.625 | 0.667 | 0.578 |
| 872條全參數微調後 | **0.000** | 0.042 | 0.042 | **0.048** |
| *對照:139條全參數微調(舊)* | *0.167* | *0.250* | *0.250* | *0.218* |

**這是最反直覺的一次結果**:語料量從139條增加到872條,全參數微調的 MRR 不是從0.218回升,而是進一步崩到0.048,比原本更差,Recall@1直接掉到0。

推測原因:3 epoch下,語料量變大直接讓每個epoch的訓練step數等比例增加(139條約54個step,872條約327個step,增加6倍)。訓練目標(TSDAE去噪重建)跟下游任務(語義檢索排序)的不一致性沒有因為語料變多而消失,更多的訓練step等於讓模型在錯誤的方向上走得更遠、偏離原本通用語義空間更徹底。

### 拆解混淆變數:語料量跟訓練step數,兩個都有份

上面的推測有一個問題:語料量跟訓練step數是綁在一起變動的(3 epoch下,語料變大,step數自動跟著變大),沒辦法確定「語料本身」還是「訓練跑太多步」才是真正原因。做了一個消融實驗把兩者拆開:維持872條語料不變,但用 `steps_per_epoch` 把總訓練step數直接鎖定在跟139條語料時完全一樣的54步。

| 條件 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| Baseline(872條,未微調) | 0.500 | 0.625 | 0.667 | 0.578 |
| 872條語料 + 327 step | 0.000 | 0.042 | 0.042 | 0.048 |
| **872條語料 + 54 step(鎖定)** | **0.125** | **0.125** | **0.167** | **0.141** |
| 139條語料 + 54 step(舊) | 0.167 | 0.250 | 0.250 | 0.218 |

**結果不是單一原因能解釋的,兩個變數都有份**:把872條語料的訓練step數從327降到54,MRR從0.048回升到0.141,證實「訓練step數太多」確實是傷害的主因之一——少走了6倍的step,傷害減少了將近3倍。但即使把step數鎖定成跟139條語料完全一樣,872條語料的結果(MRR 0.141)還是比139條語料本身的結果(MRR 0.218)更差——代表「語料本身」也造成了額外的傷害,不是只有step數的問題。

比較合理的解釋是:新增的733條語料來自23個相關但不完全相同的公務人員法規類別,主題比原本4部法規更發散,這種話題轉移(topic shift)本身也會稀釋/干擾去噪重建任務學到的方向,跟step數的影響是疊加的,不是互斥的兩個獨立假說。這個結果比一開始設想的「單一原因」更貼近真實情況,也讓整條研究線的結論更嚴謹:**災難性遺忘在小資料情境下,由「訓練走了多少步」跟「語料本身跟任務的一致性」共同決定,不能只調其中一個變數就宣稱解決問題**。

## 研究歷程

### 研究動機與路徑

這個專案原本只是一個「能回答」的 LINE Bot,沒有任何量化過的檢索品質數據。開始補評估集之後,自然浮現一個問題:**要不要順手做個「無監督領域微調」讓 embedding 更貼近法規領域的語言風格?** 這是很多 RAG 專案常見的下一步,理論上只用語料本身(不需要人工標註問答配對)就能做。實際跑出來卻是全面負向的結果(MRR 0.555 → 0.218),而且跟另一個專案(`food-violation-severity-model` 的 BERT 微調負向結果)是同一種「直覺上該更好、實際更差」的模式,讓我開始認真思考這背後是不是同一個原因:**資料量太小時,微調本身就是風險最高的選擇**。

從這個觀察出發,研究路徑分成四步往下走:
1. **先確認方向**:全參數微調在小語料上是否真的是「動了太多權重」導致的災難性遺忘?→ 用 LoRA(只調0.13%參數)做對照實驗驗證
2. **意外的分支**:驗證過程中 LoRA 第一次嘗試就失敗了,而且是跟原本假設不同的失效模式(表徵坍縮,不是遺忘)→ 停下來先把這個意外插曲除錯清楚,而不是跳過
3. **驗證另一個可能的解法**:如果不用 LoRA,單純加大語料量能不能達到一樣的效果?→ 擴充語料到872條重新測試,得到「反而更差」的反直覺結果,初步推測是訓練step數等比例放大導致的
4. **拆解混淆變數**:第3步的語料量跟訓練step數是綁在一起變動的,不能直接下結論→ 設計消融實驗,鎖定872條語料的訓練step數跟139條時一致,結果發現兩個變數都有影響,不是單一原因——這比原本設想的更嚴謹,也更貼近真實情況

### 研究方法

- **對照實驗設計**:全程只變動一個變數(可訓練參數比例 / 語料量),其餘超參數(epoch數、batch size、學習率、訓練目標)保持一致,確保能把差異歸因到單一變數上
- **獨立評估集**:24題人工標註問答對,跟訓練/建庫語料完全不重疊,避免資料洩漏讓數字虛高
- **不只看最終分數,直接檢查中間產物**:LoRA表徵坍縮那次,是直接算 embedding 之間的 cosine 相似度、檢查是否有 NaN 才抓到問題,不是單純看 MRR 掉了就停止分析
- **失敗後回頭做機制性解釋**,而不是只記錄「有效/無效」:872條語料反而更差時,回頭去算訓練 step 數(139條→54 step,872條→327 step)去解釋「為什麼」,而不只是報告「結果更差」

### 遇到的困難與除錯

- **環境問題**:`transformers`/`sentence-transformers` 版本不相容,`tensorboard`/`tensorflow` 未安裝導致直接crash,`compute_loss()` 參數簽章不相容——都用 monkeypatch 繞過,才能真正跑起實驗,而不是卡在環境設定
- **LoRA 表徵坍縮**:依照「LoRA可以用更高學習率」的常見經驗法則設定 lr=3e-4,結果比全參數微調還差(MRR=0.024)。一開始以為是遺忘更嚴重,實際打開 embedding 檢查才發現是完全不同的失效模式(任兩篇不同法規條文的 embedding cosine 相似度高達0.9996)。調回跟全參數微調一致的 lr=3e-5 才成功
- **語料擴充時的 ID 格式不一致**:外部語料庫(`lianghsun/tw-law`)的條號格式跟既有語料不同(`第 1 條` vs `第3條`,多一個空白),合併前先做正規化,並在合併後明確驗證24題評估集的 gold_id 全部還在擴充後的語料庫裡,才開始訓練——避免「換了語料庫導致某些題目變成不可能答對」這種會讓比較失真的隱藏bug

### 時程(依實際執行順序)

1. 補上 24 題人工標註評估集 + baseline 檢索評估
2. 139條語料全參數 TSDAE 微調 → 得到第一個負向結果(MRR 0.218)
3. 設計 LoRA 對照實驗驗證災難性遺忘假設 → 第一次嘗試(高學習率)失敗,診斷出表徵坍縮 → 調整學習率後成功驗證假設(MRR 0.544)
4. 從 Hugging Face 找到可信的公開法規語料源,擴充語料到872條,驗證「單純加大語料量」這條路徑 → 得到「反而更差」的反直覺結果(MRR 0.048)
5. 設計消融實驗拆解「語料量」跟「訓練step數」這兩個混淆變數 → 鎖定872條語料的step數跟139條一致,MRR回升到0.141但仍不如139條的0.218 → 確認兩個變數都有影響,不是單一原因
